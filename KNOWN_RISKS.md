# Known Risks & TODOs

## Wallet Integration
- **Lace `shieldedAddress` parsing**: In `frontend/src/walletAdapter.ts`, the decoding logic for extracting `ShieldedCoinPublicKey` and `ShieldedEncryptionPublicKey` from the Lace-provided `shieldedAddress` string is verified against self-generated (encode→decode round-trip) test data only. Not yet verified against a live Lace-issued address. First live Deploy button click against a real connected wallet is the actual verification of this path — treat any failure there as highest priority, starting here.

## Secret Distribution
- **Issuer-Distributed `salt`**: Currently, the `salt` required for credential commitments is randomly generated by the issuer and must be securely distributed to the holder (along with the `credentialType` and `issuerId`). If the holder loses this `salt`, they can never prove the credential again, even if they have their `holderSecret`. A more robust future design would be to deterministically derive `salt = hash(holderSecret, publicIssuanceNonce)` so the holder only ever needs to backup their `holderSecret`. We opted for the issuer-distributed version now to avoid altering the compiled Compact circuit data structures in this pass, but this should be refactored before production to minimize holder data-loss vectors.
